    Code Standards

    Frontend Standards (Next.js, TypeScript, Tailwind)

    Components

    • Always use functional components for consistency and performance.
    • Example:
      ```typescript // Good export function UserCard({ name }: { name: string }) { return
      {name}
      ; }
      // Avoid
class UserCard extends React.Component {
  render() {
    return <div>{this.props.name}</div>;
  }
}
```

    Naming Conventions

    • camelCase for variables and functions
      const userName = 'John';
      function getUserData() {}
    • PascalCase for component names
      function UserProfile() {}
    • SCREAMING_SNAKE_CASE for constants
      const API_BASE_URL = '...';

    File Structure

    • One component per file.
    • Group files by feature/module for maintainability.
    • Example Directory Structure: src/ components/ UserCard.tsx UserProfile.tsx features/ dashboard/ DashboardPage.tsx DashboardChart.tsx

    Testing

    • Use Jest and React Testing Library for unit tests.
    • Add tests for every new component or logic.
    • Example: ```typescript import { render, screen } from '@testing-library/react'; import UserCard from './UserCard';

    test('renders user name', () => { render(); expect(screen.getByText('Alice')).toBeInTheDocument(); }); ```

    Styling

    • Use Tailwind CSS for all styling.

    Backend Standards (Django, DRF)

    Naming Conventions

    • snake_case for variables and functions
      user_name = "John"
    • PascalCase for classes and models
      class UserProfile(models.Model):

    Serializers & Views

    • Place each serializer or view in its own file unless closely related.
    • Example: users/ serializers.py views.py urls.py

    Testing

    • Use Django’s built-in test runner (python manage.py test) and maintain high test coverage.
    • Example: ```python from django.test import TestCase from .models import UserProfile

    class UserProfileTestCase(TestCase): def test_str(self): user = UserProfile.objects.create(name="jacky") self.assertEqual(str(user), "jacky") ```

    Best Practices

    1. Keep Functions and Components Small & Focused

    • Each function/component should do one thing only.
    • Aim for less than 50 lines per function/component.
    • Split complex logic into smaller helpers/utilities.
    • Bad Example: typescript // Too much logic in one function/component function Dashboard() { // data fetching, filtering, rendering, and event handling all in one place }
    • Good Example: typescript function Dashboard() { const data = useDashboardData(); return <DashboardTable data={filteredData(data)} />; } function filteredData(data) { ... }

    2. Prefer Composition Over Inheritance

    • Build features by composing simple, reusable components/functions rather than relying on class inheritance.
    • Example: tsx // Good: Compose smaller components <Card> <CardHeader /> <CardBody /> </Card>

    3. Handling Commented-Out Code

    • Do not commit commented-out code unless it clarifies complex logic or algorithms.
    • If needed, add a comment explaining why it remains.
    • Remove commented code as soon as it is no longer necessary.
    • Example: python # Used for debugging edge case in production - remove after release # print("DEBUG: user_id", user_id)

    4. Refactor & Remove Unused Code Regularly

    • Before every PR: Review and clean up unused or obsolete code.
    • Sprint-end: The team should perform code cleanup at the end of every sprint or milestone.
    • Use IDE features and tools like ESLint (frontend) and flake8 (backend) to identify unused code.
    • Code reviewers must also flag unused or commented-out code.

    5. Lint & Test Before Every Commit

    • Run all linters and automated tests before every commit (not just before merging).
    • If tests or linting fail, resolve errors before committing.
    • If stuck, seek help from the team before submitting a PR.

    6. Follow Naming & File Organization Conventions

    • Use camelCase, PascalCase, and snake_case as specified.
    • Organize files by feature/module for easier navigation and maintenance.

    7. Write Clear Commit Messages & PR Summaries

    • Each commit/PR should explain what changed and why.
    • Reference any related issues.

    8. General Workflow Expectations

    • Always branch from the latest develop branch and open PRs into develop (not main).
    • Test changes locally before pushing.
    • Request at least one code review before merging.
