    Deployment Process

    Frontend Deployment

    Platform:
    Vercel

    Deployment Branch:
    Auto-deployment is enabled from the main branch. Only merges to main trigger a production deployment. --

    Pre-Deployment (Local Build):
    Before pushing code, always run a local production build to catch issues early:

    npm run build

    Build & Preview Process:

    • Each push or pull request (PR) automatically triggers a Vercel preview build.
    • Preview URLs are available both in the PR (on GitHub) and in the Vercel dashboard.
    • Merging to the main branch triggers a production deployment.
    • To view a build preview, open your PR on GitHub and look for the "Vercel Preview" check.

    Failure:

    • If deployment fails, review build logs and errors in the Vercel dashboard under "Deployments."
    • Resolve any issues and push a new commit to trigger a redeployment.
    • To rollback, revert the main branch to a previous working commit and redeploy.

    Backend Deployment

    Platform:
    Heroku

    Deployment Trigger and Access:
    The admin deploys after merging all approved PRs to develop and then to main. Only the admin and one developer have Heroku dashboard access. The developer can view logs only; only the admin can deploy.

    Pre-Deployment (Local Build/Test):
    Before deploying, always run local tests and collect static files:

    python manage.py test
python manage.py collectstatic --noinput

    Ensure all tests pass and static files are collected without errors.

    Environment Variables:
    Environment variables are managed in the Heroku dashboard under Settings → Config Vars. Document all variables in an internal config file for future reference. All new variables must be reviewed and approved in PRs.

    Scaling:
    Heroku dynos scale automatically by default for most use-cases.

    Manual Steps (e.g., Migrations):
    If the deployment includes database schema changes, run migrations:

    heroku run python manage.py migrate --app <heroku-app-name>

    Check for migration errors and confirm data integrity.

    Failure & Rollback:
    If deployment fails, check logs using:

    heroku logs --tail --app <heroku-app-name>

    Fix issues and redeploy. If urgent, rollback using:

    heroku releases:rollback --app <heroku-app-name>

    Always notify the team and document the incident.

    Monitoring:
    Use the Heroku dashboard for logs, status, and metrics.

    CI/CD Pipeline

    Tool:
    GitHub Actions

    Workflow:
    Every push and PR triggers automated tests (unit and integration), builds, and lint/code quality checks. If all checks pass, code can be merged and deployed.

    Secrets Management:
    API keys, tokens, and other sensitive secrets are securely stored as GitHub Actions Secrets. Never commit secrets to the repository. To add or update secrets, go to the repo’s Settings → Secrets and variables → Actions, and notify the admin.

    Deployment Automation:
    On merge to main, GitHub Actions triggers production deployments for frontend (to Vercel) and backend (Heroku). Build/test status is visible on PRs and in the GitHub Actions tab.

    Failure Handling:
    If a workflow fails, check logs in the Actions tab, fix issues, and re-run as needed. Escalate unresolved failures to the admin or a senior developer.

    General Deployment Checklist

    1. Ensure all code is reviewed and merged into the appropriate branch.
    2. Confirm all required environment variables are documented and set in their dashboards.
    3. Run all tests locally before pushing code.
    4. Monitor the deployment process using Vercel/Heroku dashboards and/or GitHub Actions.
    5. After deployment, verify the application by running manual checks, smoke tests, or automated post-deploy checks.
    6. If issues arise, follow the rollback procedures and clearly communicate with the team.

    Access & Permissions

    Only the admin and one designated developer have production deployment and dashboard access (Vercel/Heroku). The developer has access to logs only on Heroku; only the admin can deploy. For access requests, contact the admin. The onboarding documentation should explain this process.
